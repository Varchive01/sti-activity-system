STI-ARMES Faculty Module — Comprehensive Functional and UI/UX Audit Report

System Inspection, Component Testing, Security Boundaries & UI/UX Audit | Date: November 9, 2026 | Test Account: Maria Santos (faculty@sti.edu)

1. Executive Summary

A rigorous, end-to-end functional and UI/UX audit was conducted on the Faculty Account and all its accessible modules within the STI Activity Request, Monitoring, and Evaluation System (STI-ARMES). Testing encompassed both the live hosting domain (https://sti-armes.freedev.app/) and the local development environment (http://localhost/sti-activity-system/) using authorized faculty test credentials (Maria Santos, faculty@sti.edu, ID 387). The audit inspected 20 distinct pages and routes, evaluated over 530 interactive components, verified 12 comprehensive workflow lifecycles, and captured 23 genuine high-resolution screenshots.

The evaluation revealed that core architectural capabilities—such as role-based access control (RBAC), multi-step proposal creation, offline draft synchronization, timeline visualization, and automated text formatting—are robustly engineered and successfully protect unauthorized access. However, specific functional, data-architecture, and UI/UX deficiencies were identified, including hardcoded faculty rosters, legacy unparameterized SQL interpolations in secondary views, placeholder duplicate KPI pages, and minor responsive layout wrapping on task filter controls. In accordance with audit protocol, no source files were modified during this assessment.

5. Identified Defects, Bugs & Inconsistencies

IDSeverityPage / RouteAffected ComponentObserved Defect / FindingRecommended Correction
ISSUE-FAC-01 High faculty/proposal-create.php & proposal-edit.php Faculty Task Assignment Optgroups The faculty roster in renderFacultyTaskOptgroups() is statically hardcoded in an array ($facultyDepartmentGroups) with fixed names. When new faculty register or profiles change, the dropdown is desynchronized from the actual database users table. Replace hardcoded array with dynamic population from getEligibleFacultyMembers($db) grouped by user.department.
ISSUE-FAC-02 Medium faculty/pending.php & faculty/approved.php SQL Database Query Execution Queries in pending.php (line 23) and approved.php (lines 16-38) use direct variable string interpolation (WHERE a.faculty_id = {$user['id']}) rather than PDO prepared statements with parameterized inputs. Refactor all SQL queries to use $db->prepare(...) and $stmt->execute([$user['id']]).
ISSUE-FAC-03 Medium faculty/kpi-overview.php & faculty/kpi-reports.php Secondary KPI Reporting Pages kpi-overview.php and kpi-reports.php are identical legacy duplicate stubs that list activities without rendering any actual KPI metrics. They are not linked in the sidebar and create code redundancy. Consolidate both files into redirects pointing to the primary faculty/kpi.php, or upgrade them to display departmental comparative analytics.
ISSUE-FAC-04 Low faculty/tasks.php Task Filter Control Responsive Layout On screen viewports between 1024px and 1280px, the 6 task filter dropdowns wrap unevenly, causing the 'Search task, activity, role' input and button to drop to a second line with awkward left alignment. Apply CSS flexbox wrapping or a standardized CSS grid (grid-template-columns: repeat(auto-fit, minmax(180px, 1fr))) to maintain uniform alignment.
ISSUE-FAC-05 Low faculty/dashboard.php Walkthrough Modal Target Alignment in Dark Mode When switching between Dark Theme and Light Theme, the walkthrough popover balloon border-color uses a semi-transparent border that has low contrast against dark card headers. Update walkthrough.css to use var(--border) and var(--accent) dynamically across both light and dark themes.
ISSUE-FAC-06 Low faculty/proposal-create.php Direct Step Jumping via URL Query Parameter Users can manually enter URL parameters like ?step=4 without completing Steps 1-3. While backend submission validation prevents saving an incomplete proposal, the UI does not redirect the user back to the first incomplete step. Add a client-side and server-side step guard that verifies required Step 1 fields before allowing navigation to Step 2, 3, or 4.

7. Role-Based Access Control (RBAC) Assessment

A critical mandate of the audit was verifying security boundaries between user roles. Five unauthorized routes were directly accessed using the authenticated Faculty session:

  • /admin1/dashboard.php (Student Org Academic Approver): BLOCKED. Safely denied/redirected (PASSED)
  • /admin2/dashboard.php (Academic Affairs Approver): BLOCKED. Safely denied/redirected (PASSED)
  • /dean/dashboard.php (Dean Oversight): BLOCKED. Safely denied/redirected (PASSED)
  • /program_head/dashboard.php (Program Head Oversight): BLOCKED. Safely denied/redirected (PASSED)
  • /admin1/users.php (User Management): BLOCKED. Safely denied/redirected (PASSED)

Private draft isolation was also verified: Faculty users can only view their own drafts or proposals where they have been explicitly invited as active collaborators via the proposal_collaborators table. Private unsubmitted drafts belonging to other faculty members remain completely hidden.

8. Overall Assessment & Conclusion

The STI-ARMES Faculty Module demonstrates a mature, robustly architected foundation for academic activity proposal submission, timeline management, deliverable tracking, and post-event reporting. Role-based security boundaries are strictly enforced, and client-side draft auto-saving prevents data loss during complex multi-step proposal authoring. The identified issues are predominantly architectural enhancements (dynamic faculty roster resolution, PDO parameterization on secondary queries, and retirement of unused duplicate stub files) rather than catastrophic blockers. Implementing the recommended corrections upon stakeholder authorization will further solidify the platform's stability, maintainability, and capstone manuscript defensibility.
